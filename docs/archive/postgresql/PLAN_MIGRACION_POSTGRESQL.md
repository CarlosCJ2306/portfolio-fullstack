# Plan integral de migración de SQLite a PostgreSQL

Estado: planificación únicamente. No se ejecutó una migración ni se abrió conexión PostgreSQL.

## 1. Objetivo

Migrar de manera reproducible el esquema, los datos y las relaciones del portfolio desde SQLite a PostgreSQL, ensayando primero en desarrollo/testing y staging, con preservación de IDs, validación de multimedia y rollback documentado.

## 2. Motor y configuración actual

- Motor: SQLite mediante SQLAlchemy 2.
- Fuente local: `backend/portfolio.db`, fuera de Git.
- Configuración: `DATABASE_URL`, con valor local relativo resuelto contra la raíz backend.
- Conexiones SQLite: `check_same_thread=False` y evento que ejecuta `PRAGMA foreign_keys=ON`.
- Sesiones: `sessionmaker` sin autocommit ni autoflush.
- Integridad observada en C0: `integrity_check=ok` y cero violaciones de FK.

## 3. Inventario de tablas

| Tabla | Propósito | PK |
|---|---|---|
| `profile` | Perfil público | `id` entero |
| `social_links` | Redes/canales | `id` entero |
| `skills` | Catálogo técnico | `id` entero |
| `projects` | Proyectos | `id` entero |
| `project_skills` | Proyecto ↔ skill | PK compuesta (`project_id`, `skill_id`) |
| `project_images` | Galería ordenada | PK compuesta (`project_id`, `media_asset_id`) |

| `experience_bullets` | Bullets de experiencia | `id` entero |

| `contact_messages` | Mensajes privados | `id` entero |

Antes de migrar se debe incorporar cualquier campo aprobado en C1 mediante esquema versionado, tanto en SQLite como en la definición PostgreSQL.

## 4. Claves foráneas y relaciones

- `profile.avatar_asset_id → media_assets.id`.
- `skills.icon_asset_id → media_assets.id`.
- `projects.image_asset_id → media_assets.id`.
- `project_images.project_id → projects.id` con `ON DELETE CASCADE`.
- `project_images.media_asset_id → media_assets.id` con `ON DELETE RESTRICT`.
- `project_skills.project_id → projects.id`.
- `project_skills.skill_id → skills.id`.
- `experience_bullets.experience_id → experiences.id`.
- `certifications.certificate_file_id → media_assets.id` con `ON DELETE SET NULL`.

La migración debe recrear explícitamente las acciones `ON DELETE`, índices, constraints únicos y orden lógico; no basta con copiar columnas.

## 5. Tipos de datos

- `INTEGER`: PK, FK, años y orden.
- `VARCHAR(n)`: nombres, títulos, URLs, MIME y metadatos cortos.
- `TEXT`: descripciones, mensajes, Base64 y SVG.
- `BOOLEAN`: publicación, destacado, actual, leído.
- `DATE`: periodos profesionales y certificaciones.
- `DATETIME`: auditoría `created_at`/`updated_at`.

Mapeo PostgreSQL recomendado: `INTEGER`, `VARCHAR`, `TEXT`, `BOOLEAN`, `DATE` y `TIMESTAMP WITH TIME ZONE` cuando los modelos realmente produzcan datetimes conscientes. Verificar los valores históricos antes de convertir zona horaria.

## 6. Booleanos

SQLite almacena booleanos con afinidad entera; PostgreSQL exige valores booleanos. El exportador debe convertir `0/1` a `false/true`, rechazar valores fuera del dominio y comparar conteos por estado.

## 7. Fechas y timestamps

- Fechas `DATE` deben transferirse como ISO `YYYY-MM-DD`, sin conversión de zona horaria.
- Timestamps deben normalizarse a UTC y conservar precisión compatible.
- Valores nulos se mantienen nulos.
- No corregir fechas profesionales durante la migración; las correcciones editoriales pertenecen a C3.

## 8. Textos y codificación

Usar UTF-8 extremo a extremo. Comparar longitud y hash de textos relevantes, comprobar tildes y evitar transformaciones automáticas de mojibake. Nunca registrar contenido privado o Base64 completo.

## 9. JSON

El esquema actual no tiene columnas JSON. Las listas se modelan con tablas relacionales. No convertir relaciones a JSONB durante esta migración; sería un cambio arquitectónico distinto.

## 10. Autoincrementales y secuencias

Los `INTEGER PRIMARY KEY` de SQLite se migrarán conservando IDs. PostgreSQL debe usar `GENERATED BY DEFAULT AS IDENTITY` o secuencias compatibles con SQLAlchemy. Después de importar, reajustar cada secuencia a `MAX(id)` y probar una inserción transaccional controlada.

## 11. Multimedia y Base64

`media_assets` guarda `data_base64` o `svg_content`. Para la primera migración se preserva el contrato actual; mover archivos a object storage pertenece a Producción 1/una fase independiente.

Validaciones:

- conteo por `asset_type`;
- longitud y SHA-256 del contenido sin imprimirlo;
- MIME y extensión coherentes;
- decodificación de muestras autorizadas;
- referencias de avatar, icono, portada, galería y certificado;
- política SVG segura.

Los payloads grandes siguen siendo riesgo productivo aunque PostgreSQL los soporte.

## 12. Diferencias SQLite/PostgreSQL

| Tema | SQLite | PostgreSQL | Acción |
|---|---|---|---|
| FK | Requiere PRAGMA por conexión | Siempre aplicadas | Condicionar evento al dialecto y validar constraints. |
| Concurrencia | Escritura limitada por archivo | MVCC/múltiples conexiones | Configurar pool y timeouts. |
| Booleanos | Afinidad entera | Tipo estricto | Transformar y validar dominio. |
| Identidad | `INTEGER PRIMARY KEY` | Identity/secuencia | Preservar IDs y reajustar secuencias. |
| DateTime | Flexible | Tipo estricto | Normalizar timestamps. |
| Comparación | Collation/LIKE particulares | Reglas distintas | Probar búsquedas, unicidad y case sensitivity. |
| DDL | Scripts puntuales | Migraciones transaccionales más completas | Adoptar Alembic. |
| Ruta | Archivo local | Servicio de red/TLS | Variables, secretos, SSL y pool. |

## 13. Driver requerido

Recomendación: `psycopg` 3 compatible con SQLAlchemy. Fijar versión en `requirements.txt`; usar variante binaria solo donde sea apropiado. La URL objetivo será del tipo `postgresql+psycopg://...`, siempre suministrada por secretos del entorno.

## 14. DATABASE_URL

- Mantener una sola variable contractual.
- No registrar credenciales; usar `_mask_database_url`.
- Exigir SSL según proveedor.
- Separar development, test, staging y production.
- Fallar de forma segura si producción recibe la URL SQLite o credenciales por defecto.

## 15. Cambios en SQLAlchemy

1. Mantener `_build_connect_args` específico de SQLite.
2. Registrar PRAGMA solo para dialecto SQLite.
3. Configurar opciones de pool PostgreSQL (`pool_pre_ping`, tamaños y timeouts) con valores de entorno prudentes.
4. Revisar `DateTime(timezone=True)` y defaults UTC.
5. Nombrar constraints para migraciones reproducibles.
6. Probar loaders, cascadas y restricciones en ambos motores.
7. No introducir SQL específico de PostgreSQL en repositorios sin abstracción justificada.

## 16. Estrategia Alembic

1. Añadir Alembic y configurar `target_metadata=Base.metadata`.
2. Definir convención de nombres para índices/FK/UK.
3. Crear baseline revisada manualmente del esquema vigente.
4. Incorporar primero los cambios C1 como revisiones aditivas.
5. Probar `upgrade head` desde DB vacía en SQLite temporal y PostgreSQL temporal.
6. Probar downgrade solo donde sea seguro; una reversión de datos requiere backup.
7. Nunca ejecutar `create_all` ni seed general como sustituto de migraciones en producción.

## 17. Backup previo

- Congelar escrituras.
- Crear backup SQLite consistente mediante API de backup.
- Verificar tamaño, apertura read-only, `integrity_check` y `foreign_key_check`.
- Cifrar y almacenar fuera de Git y del artefacto desplegado.
- Registrar hash, fecha, versión de esquema y conteos sin datos privados.

## 18. Exportación

Crear un exportador de solo lectura, idempotente y reanudable:

1. Abrir SQLite con URI `mode=ro`.
2. Exportar en orden de dependencias a estructuras en memoria/lotes o formato seguro cifrado.
3. Conservar IDs y valores nulos.
4. Generar manifiesto de conteos/hashes.
5. No escribir Base64, mensajes ni credenciales en consola.

## 19. Transformación

- Normalizar booleanos y timestamps únicamente.
- Validar UTF-8 y longitudes contra columnas objetivo.
- No alterar contenido editorial ni anonimizar durante el transporte: C3 debe dejar la fuente aprobada antes de migrar.
- Rechazar filas inválidas y abortar el lote completo; no “arreglar” silenciosamente.

## 20. Importación

Orden sugerido:

1. `media_assets`, `profile`, `social_links`, `skills`, `experiences`, `education`, `certifications`, `projects`, `contact_messages`, `users`.
2. `experience_bullets`.
3. `project_skills` y `project_images`.
4. Ajuste de secuencias.

Ejecutar en transacción o lotes con punto de control. En un ensayo fallido, descartar la DB de staging y repetir; no continuar con datos parciales.

## 21. Validación posterior

- Conteos totales y activos por tabla.
- IDs mínimos/máximos y secuencias.
- Cero FK huérfanas mediante anti-joins.
- Unicidad de slug y skill.
- Igualdad de relaciones de proyecto/skills/galería.
- Igualdad de hashes multimedia.
- Perfil/avatar, certificación/PDF y mensajes intactos.
- Fechas, booleanos, orden y caracteres españoles correctos.

## 22. Pruebas

- Suite backend completa parametrizada por PostgreSQL temporal.
- Tests de migración desde fixture SQLite representativa.
- Idempotencia/control de reejecución.
- CRUD y rollback transaccional.
- Protección de assets referenciados.
- Uploads, SVG, PDF y límites.
- Contratos públicos/admin.
- Lint/build y checklist frontend contra staging.
- CORS, HTTPS, reinicio y persistencia.

## 23. Entornos

### Desarrollo

SQLite puede mantenerse para trabajo ligero solo si las pruebas corren también en PostgreSQL. Preferible usar PostgreSQL local mediante contenedor o servicio efímero para detectar diferencias pronto.

### Testing

Crear una base aislada por ejecución, credenciales efímeras y limpieza completa. Prohibir URLs de producción mediante guardas equivalentes a las pruebas SQLite actuales.

### Staging

Restaurar una copia sanitizada o protegida del dataset real. Ejecutar migración completa, QA y ensayos de backup/restore. Acceso restringido y secretos gestionados por proveedor.

### Producción

Solo después de Producción 1, C4 y staging aprobado. Aplicar ventana de escritura congelada, backup final, importación, validación, cambio de `DATABASE_URL`, despliegue y smoke tests.

## 24. Rollback

Condiciones: error de importación, conteos distintos, FK huérfanas, hash multimedia distinto, contrato roto o smoke test fallido.

Procedimiento:

1. Detener escrituras PostgreSQL.
2. Revertir aplicación/configuración a la versión SQLite previa.
3. Restaurar el backup verificado si la fuente se hubiera alterado.
4. Si PostgreSQL recibió escrituras nuevas, exportarlas a un área segura para reconciliación manual; no sobrescribir SQLite.
5. Documentar incidente y no reintentar hasta corregir la causa en staging.

No eliminar SQLite ni backups hasta validar producción y su restauración.

## 25. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Pérdida de datos/IDs | Backup verificado, preservación de PK y manifiestos. |
| FK rotas | Orden de importación, constraints y anti-joins. |
| Secuencias desfasadas | `setval`/identity reset y prueba de inserción. |
| Base64 corrupto | Hash/longitud y decodificación controlada. |
| Secretos en logs | Enmascarado, salida por conteos y revisión de artefactos. |
| Diferencias de booleanos/fechas | Transformación explícita y tests cruzados. |
| Payload excesivo | Resolver Producción 1 antes del despliegue. |
| Downtime/divergencia | Congelamiento de escrituras y ventana de corte. |
| Proveedor no disponible | Backup exportable, rollback y restauración ensayada. |
| Datos confidenciales en staging | Acceso mínimo, cifrado y política de retención. |

## 26. Criterios de aceptación

- Alembic reproduce el esquema desde cero.
- Conteos, IDs, relaciones y hashes coinciden.
- Cero FK huérfanas y secuencias correctas.
- Tests backend y frontend aprobados contra PostgreSQL.
- Persistencia tras reinicio y restore ensayado.
- Sin secretos/DB/backups en Git o logs.
- C4 y Producción 1 cerradas.
- Rollback documentado y probado.

1. Resolver decisiones de C0.
2. Ejecutar C1–C4.
